# Security Code Review -- AbsenzFlow

**Date:** 2026-03-18
**Reviewer:** Claude Opus 4 (with User Seyfried)
**Scope:** Full codebase -- backend, frontend, WordPress plugin, Docker infrastructure

## Executive Summary

The AbsenzFlow codebase demonstrates solid security fundamentals: parameterized ORM queries (no SQL injection), HMAC constant-time secret comparison, UUID-based file storage, structured permission checks, and rate limiting on auth endpoints. However, the review identified **28 unique findings** across 5 severity levels, with the most critical issues concentrated in the WordPress PHP proxy layer and infrastructure configuration.

| Severity | Count |
|----------|-------|
| Critical | 2 |
| High     | 5 |
| Medium   | 13 |
| Low      | 8 |

## Critical

### C1. API Secret Logged to PHP Error Log

**File:** `wordpress-plugin/includes/class-api-proxy.php:152-153`

The shared `WORDPRESS_PROXY_SECRET` (first 10 characters + length) is written to the PHP error log on every proxied request:

```php
error_log('AbsenzFlow Proxy: API Secret (first 10 chars): ' . substr($api_secret, 0, 10) . '...');
error_log('AbsenzFlow Proxy: API Secret length: ' . strlen($api_secret));
```

Anyone with access to `wp-content/debug.log` (shared hosting, log aggregation, other plugins) can reconstruct or brute-force the secret.

**Fix:** Remove these lines entirely. Log only a boolean indicating whether the secret is set.

### C2. SSRF via Unvalidated Proxy Endpoint Parameter

**File:** `wordpress-plugin/includes/class-api-proxy.php:165,171`

The `proxy_request` method concatenates the client-supplied `endpoint` parameter directly into the backend URL with no validation:

```php
$url = rtrim($api_url, '/') . '/' . ltrim($endpoint, '/');
```

Any authenticated WordPress user can invoke arbitrary backend routes, including admin-only endpoints, since the proxy forwards the user's WordPress role without path-level enforcement.

**Fix:** Validate `endpoint` against an allowlist of permitted API path prefixes (e.g., must match `^(absences|auth|admin)/`). Reject values containing `..`, `://`, or `@`.

## High

### H1. Docker Container Runs as Root

**File:** `backend/Dockerfile`

The Dockerfile never creates or switches to a non-root user. A compromised application has root-level access to the container filesystem.

**Fix:** Add a non-root user:
```dockerfile
RUN addgroup --system app && adduser --system --ingroup app app
RUN mkdir -p /app/uploads && chown -R app:app /app/uploads
USER app
```

### H2. SSL Certificate Verification Disabled in All Proxy Requests

**Files:** `wordpress-plugin/includes/class-api-proxy.php:203,314,385,479`

All four proxy functions (API request, file upload, file download, PDF download) disable SSL verification. The shared secret travels over these unverified connections.

**Fix:** Make SSL verification configurable via a WordPress admin setting, defaulting to `true`. Only allow disabling in development.

### H3. Outdated Dependencies with Known Vulnerabilities

**File:** `backend/requirements-base.txt`

Key packages pinned to January 2024 versions:
- `python-multipart==0.0.6` -- CVE-2024-24762 (ReDoS), fixed in 0.0.7
- `python-jose[cryptography]==3.3.0` -- unmaintained, known algorithm confusion attacks
- `passlib[bcrypt]==1.7.4` -- unmaintained (last release 2022)
- `fastapi==0.109.0` -- multiple security patches since

**Fix:** Run `pip-audit`. Update all packages. Replace `python-jose` with `PyJWT`. Replace `passlib` with direct `bcrypt`.

### H4. Client-Controlled Permission Header (`X-WordPress-Dept-Heads-Can-Complete`)

**Files:** `backend/app/api/absences.py:287-292`, `wordpress-plugin/includes/class-api-proxy.php:182,200`

The backend reads `X-WordPress-Dept-Heads-Can-Complete` from the HTTP request to expand which roles can complete absences. The WordPress proxy forwards this from a WP admin setting, but the backend cannot distinguish proxy-set headers from client-injected ones.

**Fix:** Move this setting to the backend's own configuration (environment variable or database setting) instead of trusting an HTTP header.

### H5. HTTP Header Injection via Download Pass-Through

**Files:** `wordpress-plugin/includes/class-api-proxy.php:421-424,524-527`

`Content-Type` and `Content-Disposition` headers from the backend response are passed through to the browser without sanitization. A compromised backend could inject headers enabling response splitting or XSS.

**Fix:** Validate `Content-Type` against an allowlist. Sanitize `Content-Disposition` to strip newlines/CRs and enforce `attachment` disposition.

## Medium

### M1. LDAP TLS Certificate Verification Disabled

**File:** `backend/app/services/ldap_service.py:34-35`

When SSL is enabled, `OPT_X_TLS_REQUIRE_CERT` is set to `OPT_X_TLS_NEVER`, making LDAP connections vulnerable to MITM. User passwords during bind operations could be intercepted.

**Fix:** Default to `ldap.OPT_X_TLS_DEMAND`. Add `LDAP_CA_CERT_PATH` config option.

### M2. LDAP Default Configuration Uses Plaintext (Port 389)

**Files:** `backend/app/core/config.py:43,47`, `.env.example:84-85`

Defaults to `LDAP_USE_SSL=false` on port 389. Passwords travel in plaintext.

**Fix:** Default to `LDAP_USE_SSL=true` and port 636 (LDAPS).

### M3. Excessive Debug Logging in Production Proxy

**File:** `wordpress-plugin/includes/class-api-proxy.php` (multiple locations)

Every proxy request unconditionally logs: username, user ID, backend URLs, response bodies (first 200 chars). No `WP_DEBUG` guard.

**Fix:** Wrap all debug logging in `if (defined('WP_DEBUG') && WP_DEBUG)` checks.

### M4. No Magic-Bytes Validation on File Uploads

**File:** `backend/app/services/attachment_service.py:82-84`

MIME type validation trusts the client-supplied `Content-Type` header. A file with `.jpg` extension and `image/jpeg` content-type but HTML content would pass validation. Combined with the stored MIME type being served back on download, this could enable stored XSS.

**Fix:** Use `python-magic` to detect actual file type from content bytes.

### M5. Content-Disposition Header Injection via Original Filename

**File:** `backend/app/api/attachments.py:138`

The original client-supplied filename is stored unsanitized in the database and passed to `FileResponse(filename=...)`. Special characters could cause header parsing issues.

**Fix:** Sanitize filename before storage: `re.sub(r'[^\w\s\-.]', '_', Path(file.filename).name)`.

### M6. No `reason` Field Validation Against Allowed Values

**File:** `backend/app/schemas/schemas.py:155`

The `reason` field accepts any string (max 100 chars) with no whitelist. Conditional validators for `excursion_classes` / `personal_reason` can be bypassed by inventing a reason string. Arbitrary text also ends up in email notifications.

**Fix:** Add a `@field_validator("reason")` that checks against `ALLOWED_REASONS = {"sick", "training", "excursion", "personal", "other", "official"}`.

### M7. No Maximum Date Range Limit for WebUntis Requests

**Files:** `backend/app/utils/absence_utils.py:12-48`, `backend/app/api/webuntis.py:28-101`

No maximum date span enforced. A user could request timetables spanning years, causing large external API requests and potential DoS against WebUntis.

**Fix:** Add `MAX_DATE_RANGE_DAYS = 90` check in `validate_date_range()`.

### M8. HTML Injection in Email Bodies

**File:** `backend/app/utils/email_html_utils.py:48-54,70-103,217-253`

User-controlled values (`teacher_name`, `reason`, etc.) are interpolated into HTML email templates without HTML escaping.

**Fix:** Apply `html.escape()` to all user-controlled values before insertion.

### M9. Security Validation Bypass via `SKIP_SECURITY_VALIDATION`

**File:** `backend/app/core/config.py:338`

Setting `SKIP_SECURITY_VALIDATION=true` disables all startup security checks, including default-secret detection. If set for debugging and forgotten, the app runs with known default secrets.

**Fix:** In production mode (`ENVIRONMENT=production`), refuse to skip. Always log a critical warning.

### M10. JWT Token Non-Revocable (Standalone Mode)

**File:** `backend/app/api/auth.py:646-663`

The `/logout` endpoint is a no-op. Stolen JWT tokens remain valid for 8 hours (`ACCESS_TOKEN_EXPIRE_MINUTES=480`).

**Fix:** Implement a token blocklist or reduce token lifetime to 30-60 minutes with refresh token rotation.

### M11. CDN Dependencies Without Subresource Integrity

**File:** `wordpress-plugin/includes/class-shortcode.php:32-46`

React and ReactDOM loaded from `unpkg.com` without SRI hashes. A compromised CDN could inject arbitrary JavaScript.

**Fix:** Bundle React with the Vite build and serve locally, or add SRI integrity attributes.

### M12. Audit Events Only Logged to Application Logger

**File:** `backend/app/core/audit.py:86`

Audit events go only to Python's `logging` module, not to a persistent database table. Log rotation or container restarts can lose audit data. Missing audit events for: failed auth attempts, absence deletion, rejection.

**Fix:** Write audit events to a dedicated database table. Add missing event types.

### M13. `X-Forwarded-For` Trusted Without Proxy Validation

**File:** `backend/app/core/audit.py:21-24`

The audit logger trusts `X-Forwarded-For` unconditionally. Clients can spoof their IP in audit logs.

**Fix:** Only trust forwarded headers from known proxy IPs (configure via `TRUSTED_PROXY_IPS`).

## Low

### L1. `startswith` Path Traversal Check Has Prefix-Collision Edge Case

**File:** `backend/app/services/attachment_service.py:151,186,236`

String `startswith` check could match `/app/uploads-evil/` against `/app/uploads`. Unlikely in practice but technically incomplete.

**Fix:** Use `Path.is_relative_to()` (Python 3.9+) or append `os.sep` before comparison.

### L2. CORS Allows All Methods and Headers

**File:** `backend/app/main.py:116-122`

`allow_methods=["*"]` and `allow_headers=["*"]` are overly permissive despite restricted origins.

**Fix:** Restrict to actually used methods and headers.

### L3. No Per-Absence Attachment Count Limit

**File:** `backend/app/api/attachments.py:29-91`

No limit on how many files can be attached to a single absence. Authenticated users could exhaust disk over time.

**Fix:** Add `MAX_ATTACHMENTS_PER_ABSENCE = 10` check before accepting uploads.

### L4. `skip`/`limit` Query Parameters Have No Upper Bound

**Files:** `backend/app/api/absences.py:65-66`, `backend/app/api/admin.py:43-44`

No maximum for `limit`, allowing huge queries.

**Fix:** `limit: int = Query(default=100, ge=1, le=500)`.

### L5. FastAPI Docs Exposed in Production

**File:** `backend/app/main.py:47-48`

`/docs` and `/redoc` endpoints are always available, providing a complete API map.

**Fix:** `docs_url="/docs" if settings.DEBUG else None`.

### L6. Request Size Limit Bypass via Chunked Transfer-Encoding

**File:** `backend/app/main.py:126-156`

Size limit middleware only checks `Content-Length` header. Chunked requests bypass it entirely.

**Fix:** Count actual bytes read, or use nginx `client_max_body_size` in front.

### L7. Development Compose Exposes Ports on All Interfaces

**Files:** `docker-compose.yml:15,86`

PostgreSQL (5432) and pgAdmin (5050) bound to `0.0.0.0`, accessible from the LAN.

**Fix:** Bind to `127.0.0.1` in development compose.

### L8. LDAP Connection Leak on Authentication Failure

**File:** `backend/app/services/ldap_service.py:39-84`

LDAP connections are not unbound on certain error paths (`_find_user_dn` returns None, unexpected exceptions).

**Fix:** Use `try/finally` to ensure `conn.unbind_s()` is always called.

## Positive Findings

The codebase demonstrates several strong security practices:

1. **No SQL injection risk** -- all queries use SQLAlchemy ORM with parameterized queries
2. **HMAC constant-time comparison** for the WordPress proxy secret (`hmac.compare_digest`)
3. **UUID-based filenames** for stored attachments, preventing guessing and collision
4. **Path traversal protection** using `Path.resolve()` on all file operation paths
5. **Startup secret validation** -- fail-fast approach prevents running with default secrets
6. **Rate limiting** on authentication endpoints via slowapi
7. **Input sanitization** -- HTML tag stripping, control character removal, length enforcement
8. **Security headers middleware** -- `X-Content-Type-Options`, `X-Frame-Options`, HSTS
9. **LDAP injection prevention** -- `ldap.filter.filter_format()` for parameterized queries
10. **Centralized permission service** -- all CRUD operations check authorization
11. **Chunked file reading** with size limits prevents memory exhaustion on upload
12. **Audit logging** for security-critical operations (user creation, role changes, approvals)

## Fixes

The following issues are addressed as part of this review session:

### Fix 1: Remove API Secret Logging (C1)
**File:** `wordpress-plugin/includes/class-api-proxy.php`
Remove the two `error_log()` lines that leak the shared secret. Replace with a non-sensitive existence check.

### Fix 2: Add Proxy Endpoint Validation (C2)
**File:** `wordpress-plugin/includes/class-api-proxy.php`
Add allowlist validation for the `endpoint` parameter to prevent SSRF. Only permit known API path prefixes.

### Fix 3: Guard Debug Logging Behind WP_DEBUG (M3)
**File:** `wordpress-plugin/includes/class-api-proxy.php`
Wrap all `error_log()` calls in `WP_DEBUG` checks so production does not leak operational details.

### Fix 4: Add `reason` Field Whitelist Validation (M6)
**File:** `backend/app/schemas/schemas.py`
Add `@field_validator("reason")` that checks against `ALLOWED_REASONS` to prevent conditional validator bypass.

### Fix 5: HTML-Escape User Data in Email Templates (M8)
**File:** `backend/app/utils/email_html_utils.py`
Apply `html.escape()` to all user-controlled values before HTML interpolation.

### Fix 6: Sanitize Original Filename on Upload (M5)
**File:** `backend/app/api/attachments.py`
Strip special characters from the original filename before database storage.

### Fix 7: Disable FastAPI Docs in Production (L5)
**File:** `backend/app/main.py`
Conditionally disable `/docs` and `/redoc` when `DEBUG=false`.

### Fix 8: Bind Dev Ports to Localhost (L7)
**File:** `docker-compose.yml`
Change PostgreSQL and pgAdmin port bindings to `127.0.0.1`.

### Fix 9: Non-Root Docker Container (H1)
**File:** `backend/Dockerfile`
Add `appuser` (UID 1000) with `COPY --chown` and `USER appuser` directive.

### Fix 10: Configurable SSL Verification (H2)
**Files:** `wordpress-plugin/includes/class-admin.php`, `wordpress-plugin/includes/class-api-proxy.php`
Add WP admin checkbox (default: verified). Update all 4 proxy methods + cache page to use configurable setting.

### Fix 11: Replace python-jose with PyJWT (H3)
**Files:** `backend/requirements-base.txt`, `backend/app/core/security.py`, `backend/app/api/auth.py`, tests
Swap unmaintained `python-jose` for `PyJWT[crypto]`. Compatible API — only imports changed.

### Fix 12: Replace passlib with bcrypt (H3)
**Files:** `backend/requirements-base.txt`, `backend/app/core/security.py`, tests
Swap unmaintained `passlib` for direct `bcrypt`. Rewrote `verify_password` and `get_password_hash`.

### Fix 13: Update All Dependencies (H3)
**File:** `backend/requirements-base.txt`
Updated all packages from Jan 2024 pins to latest stable ranges. Fixes CVE-2024-24762 (`python-multipart`).
